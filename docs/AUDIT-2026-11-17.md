## Correction: the Composio blocker is not real

`AUDIT-2026-11-16.md` and `Documents/BotHQ.md` both claim `COMPOSIO_API_KEY` is the
literal placeholder `ak_… # TODO` and that sign-in / connected apps / `cloud-mcp` are dead.
That is stale on two counts:

1. **The key is real.** `.env` now holds a live `ak_…` project key (no `TODO`, no whitespace).
   `GET /api/v3/toolkits` returns the full toolkit catalog.
2. **The base path is fine.** `server/src/composio.ts:9` hardcodes
   `https://backend.composio.dev/api/v3.1`. The 16th's probe used a **POST** to
   `/api/v3.1/toolkits`, which 404s (that route is GET-only); a bad method was read as a
   bad key. `v3.1` resolves correctly for `GET /toolkits`, `/auth_configs`, `/connected_accounts`.

Live proof the flow works end to end: `/api/auth/google/start` issues a Composio connect
link (`lk_RXM1qL5iaQGM`), and following it lands on a 200 Composio dashboard page offering
Gmail sign-in. So composio-backed Google sign-in, connected apps, and the `cloud-mcp`
data-plane leg are **unblocked**.

Remaining nit: `@composio/core` 0.28.0 → 0.29.0 upgrade is available (log line at boot).
Not a blocker.
